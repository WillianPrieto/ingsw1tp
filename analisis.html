Especificación de Requisitos, Modelo de Casos de Uso y Modelo de Dominio de CGrande

← Volver a Presentación Ver Conceptualización (Entrega 1) →
Propósito de la Entrega 2: Definir qué debe hacer el sistema desde la perspectiva del usuario operativo y de la lógica del negocio de la distribuidora CGrande. Se detallan los requisitos funcionales y no funcionales, el catálogo formal de casos de uso con sus especificaciones paso a paso, las entidades del modelo conceptual de dominio y las reglas de negocio rectoras.

1. Requisitos Funcionales

Los requisitos funcionales describen los servicios, cálculos y operaciones que la aplicación móvil CGrande debe ejecutar de forma obligatoria:

ID Descripción del Requisito Prioridad
RF-01 El sistema debe autenticar a cada vendedor/preventista mediante usuario y contraseña, retornando una sesión segura para autorizar las operaciones del terminal móvil. Alta
RF-02 El sistema debe permitir buscar clientes en tiempo real por Razón Social, Nombre de Fantasía o número de RUC/Cédula, mostrando su ficha básica de datos comerciales. Alta
RF-03 El sistema debe capturar la geolocalización GPS del dispositivo (latitud y longitud) para registrar o actualizar las coordenadas del establecimiento comercial del cliente. Media
RF-04 El sistema debe permitir consultar el catálogo de productos por código o texto, visualizando descripción, lista de precios unitarios y existencias de stock disponibles. Alta
RF-05 El sistema debe permitir registrar pedidos de venta asociados a un cliente específico, seleccionando la condición comercial (Contado o Crédito). Alta
RF-06 El sistema debe calcular automáticamente subtotales, descuentos y montos totales al añadir, editar o remover ítems del detalle del pedido. Alta
RF-07 El sistema debe permitir registrar presupuestos preliminares y luego convertirlos a pedidos confirmados o eliminarlos si el cliente desiste. Media

2. Requisitos No Funcionales

ID Descripción del Requisito Categoría
RNF-01 Las búsquedas de catálogo y consultas de clientes deben procesarse en menos de 2 segundos en conexiones móviles 3G/4G normales. Rendimiento
RNF-02 Todas las comunicaciones entre la app Android y el servidor backend deben viajar sobre protocolo HTTPS seguro con serialización JSON. Seguridad
RNF-03 La interfaz construida con Jetpack Compose debe ser intuitiva, con botones y campos táctiles optimizados para el uso ágil con una mano en calle. Usabilidad

3. Modelo de Casos de Uso

3.1 Actores del Sistema

  • Vendedor / Preventista (Actor Principal): Usuario operativo de terreno que interactúa directamente con la aplicación móvil en su smartphone Android. Realiza búsquedas de clientes, actualiza ubicaciones GPS, consulta productos, formula pedidos/presupuestos y revisa cuentas corrientes.
  • Encargado de Depósito / Despacho (Actor Secundario): Usuario interno de la empresa que visualiza a través de la base de datos y sistema central los pedidos confirmados para preparar la mercadería.
  • Administrador del Sistema: Administra altas de usuarios, configuración de listas de precios y parámetros del servidor.
  • Sistema Central / API (Actor de Soporte): Procesa transacciones, valida reglas de negocio, persiste la información y sirve datos vía REST.

3.3 Especificación Detallada de Casos de Uso Principales

CU-05 · Registrar Pedido de Venta Requisitos: RF-05, RF-06

Actor(es): Vendedor / Preventista

Precondición: El preventista inició sesión exitosamente y seleccionó un cliente válido de su cartera.

Flujo Principal:

  1. El preventista ingresa a la pantalla de nuevo pedido con el cliente previamente asignado.
  2. Selecciona la condición comercial de la transacción: Contado o Crédito.
  3. Busca un producto por nombre o código en el catálogo digital.
  4. El sistema consulta existencias y precios vigentes según la condición de venta.
  5. El preventista indica la cantidad deseada y confirma la adición del ítem.
  6. El sistema calcula el subtotal de la línea y actualiza el importe total del pedido.
  7. El preventista repite los pasos 3 al 6 para cada artículo solicitado por el comercio.
  8. El preventista revisa el resumen del pedido y presiona "Confirmar y Enviar Pedido".
  9. La aplicación transmite el pedido completo al servidor central mediante la API REST (`/pedido/registrar` o `/pedido/add`).
  10. El servidor valida la disponibilidad, almacena la transacción en la base de datos y retorna el ID único del pedido confirmado.

Flujos Alternativos:

  • 4a. Stock insuficiente: Si la cantidad solicitada supera las existencias en depósito, el sistema emite una alerta visual mostrando el saldo real disponible para ajustar la cantidad.
  • 8a. Modificación de ítems: El preventista puede pulsar sobre cualquier ítem cargado para modificar la cantidad o eliminarlo; el sistema recalcula los totales inmediatamente.
  • 9a. Fallo de conexión de red: Si no hay cobertura de datos, la app muestra un mensaje de error de conexión, reteniendo los datos del formulario para evitar la pérdida del pedido y permitir el reenvío.

Postcondición: El pedido queda registrado en la base de datos central con estado pendiente de preparación en depósito, y el importe se refleja en el Dashboard del vendedor.

CU-03 · Registrar Geolocalización GPS de Cliente Requisito: RF-03

Actor(es): Vendedor / Preventista

Precondición: El preventista se encuentra físicamente en el local del cliente con los permisos de ubicación GPS habilitados en el dispositivo Android.

Flujo Principal:

  1. El preventista ingresa a la ficha de información del cliente.
  2. Selecciona la opción "Actualizar Ubicación GPS".
  3. La aplicación solicita las coordenadas actuales (latitud y longitud) al sensor GPS del dispositivo.
  4. El sistema presenta las coordenadas capturadas y solicita confirmación al usuario.
  5. El preventista confirma la operación.
  6. La app envía los datos al endpoint `/cliente/guardarUbicacion` de la API REST.
  7. El servidor actualiza los campos de georreferenciación en la base de datos y retorna confirmación exitosa.

Flujos Alternativos:

  • 3a. GPS apagado o sin permisos: El sistema notifica al usuario y despliega la solicitud de permisos o el acceso a los ajustes de localización de Android.

Postcondición: El cliente queda georreferenciado con coordenadas exactas para las futuras rutas de entrega del camión distribuidor.

CU-07 · Consultar Cuentas y Facturas a Crédito Requisito: RF-08

Actor(es): Vendedor / Preventista

Precondición: El preventista seleccionó al cliente en pantalla y cuenta con acceso al servicio `/venta/creditos`.

Flujo Principal:

  1. El preventista selecciona la pestaña de "Historial y Créditos" del cliente.
  2. La aplicación ejecuta la consulta asíncrona hacia el servidor.
  3. El sistema despliega el listado de facturas emitidas, especificando fecha, número de comprobante, monto original y saldo pendiente.
  4. El preventista analiza el saldo deudor del comercio antes de formular una nueva solicitud de venta.

Postcondición: El preventista obtiene visibilidad completa de la solvencia del cliente en el punto de atención.

4. Modelo de Dominio

El modelo conceptual de dominio representa los conceptos, responsabilidades y relaciones principales del negocio comercial de CGrande:

Vendedor (Usuario): Representa al personal de preventa. Posee identificador, nombre, credenciales de acceso y un registro de las ventas diarias que formula en sus recorridos.
Cliente: Comercio, almacén o minimercado destinatario de las ventas. Posee RUC con Dígito Verificador (DV), Razón Social, Nombre de Fantasía, dirección, celular de contacto, coordenadas GPS (latitud/longitud) y lista de precios asignada.
Producto: Mercadería comercializada por la distribuidora. Posee código identificador, descripción, precios diferenciados (contado/crédito) y existencia física de stock en depósito.
Pedido: Documento comercial emitido por el vendedor en calle. Registra fecha, hora, condición de venta (Contado/Crédito), estado (Pendiente, Confirmado, Facturado), importe total y cliente asociado.
Detalle de Pedido: Cada línea individual del pedido, especificando el producto solicitado, cantidad de unidades, precio unitario aplicado y subtotal calculado.
Factura / Venta a Crédito: Registro de las transacciones facturadas al cliente, controlando importes cobrados, saldos vencidos y plazos de crédito otorgados.

5. Reglas del Negocio

Código Regla de Negocio
RN-01 Asociación Obligatoria de Cliente: Ningún pedido o presupuesto puede formularse sin haber seleccionado previamente un cliente con identificador fiscal válido (RUC/Cédula).
RN-02 Validación de Existencia de Stock: La aplicación no permite confirmar pedidos cuyas cantidades excedan el inventario disponible en depósito, salvo que se registre explícitamente en modo presupuesto preliminar.
RN-03 Condición Comercial y Precios: El precio unitario de los productos se determina automáticamente a partir de la condición de pago pactada (Contado o Crédito) y la lista de precios asignada al cliente.
RN-04 Control de Saldos Morosos: Si un cliente acumula facturas a crédito con vencimiento cumplido, el sistema advierte al vendedor que la operación a crédito requiere autorización administrativa superior.
RN-05 Inmutabilidad de Pedidos Despachados: Una vez que un pedido cambia de estado a "Confirmado" o "En Despacho" por parte de depósito, no puede ser modificado ni eliminado desde el terminal móvil del vendedor.
