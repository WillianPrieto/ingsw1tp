Propósito de la Entrega 2: Formalizar el análisis de requisitos y modelado conceptual para la aplicación móvil CGrande. Se detallan los requisitos funcionales y no funcionales fundamentados en la arquitectura del sistema, el catálogo de casos de uso con especificaciones rigurosas, diagramas UML (casos de uso, dominio, secuencia y actividad), el modelo de entidades y la matriz de trazabilidad completa.

1. Requisitos Funcionales

Los requisitos funcionales detallan las capacidades operativas provistas por la aplicación móvil:

ID Descripción del Requisito Prioridad
RF-01 El sistema debe autenticar al vendedor mediante usuario y contraseña, almacenando la sesión de forma persistente en el dispositivo para habilitar la operativa comercial. Alta
RF-02 El sistema debe permitir buscar clientes en tiempo real por Razón Social o RUC, visualizando su información tributaria, datos de contacto y ubicación registrada. Alta
RF-03 El sistema debe capturar las coordenadas GPS del dispositivo y permitir ubicar al comercio cliente sobre un mapa interactivo (OpenStreetMap/Nominatim) para actualizar su georreferenciación. Media

RF-06 El sistema debe permitir registrar pedidos de venta asociados a un cliente, seleccionando la condición comercial (Contado o Crédito) y calculando automáticamente subtotales y totales. Alta

2. Requisitos No Funcionales

ID Descripción del Requisito Categoría
RNF-01 Las consultas de productos y clientes deben presentar una latencia de respuesta inferior a 2 segundos bajo cobertura móvil estándar 3G/4G. Rendimiento
RNF-02 Todas las comunicaciones de red hacia la API REST corporativa (cgrande.araujoe.com) deben ejecutarse bajo protocolo seguro HTTPS con cifrado TLS. Seguridad
RNF-03 La interfaz construida con Jetpack Compose y Material 3 debe estar restringida a orientación vertical (portrait) y diseñada para uso táctil fluido con una sola mano. Usabilidad
RNF-04 El sistema debe implementar tolerancia a fallos mediante persistencia local en Room Database (DraftOrderEntity), evitando pérdidas de pedidos ante desconexiones repentinas. Confiabilidad
RNF-05 La aplicación debe ser compatible con dispositivos Android a partir de minSdk 24 (Android 7.0 Nougat) hasta targetSdk 34 (Android 14). Portabilidad

3. Modelo de Casos de Uso

3.1 Actores del Sistema

Siguiendo el estándar de modelado UML de la cátedra, los actores representan exclusivamente entidades externas que interactúan de forma directa con la aplicación:

  • Vendedor / Preventista (Actor Principal): Único usuario humano directo de la aplicación móvil. Opera el terminal Android en terreno para consultar inventario, registrar pedidos, georreferenciar clientes y emitir comprobantes.

Nota metodológica UML: El personal de depósito y la administración no son actores del sistema móvil, pues interactúan con la base de datos central a través del sistema ERP del servidor. Asimismo, la API REST central actúa como frontera tecnológica de integración y no como un actor externo.

3.4 Especificación Detallada de Casos de Uso Principales

CU-05 · Registrar y Enviar Pedido de Venta Requisitos: RF-06, RF-07

Actor: Vendedor / Preventista

Precondición: El preventista inició sesión y seleccionó un cliente de su cartera comercial.

Flujo Principal:

  1. El preventista accede a la pantalla de nuevo pedido con el cliente asignado.
  2. Selecciona la condición comercial de la transacción: Contado o Crédito.
  3. Busca artículos en el catálogo digital mediante código o descripción.
  4. El sistema consulta existencias y precios unitarios correspondientes.
  5. El preventista indica la cantidad deseada y agrega el ítem al pedido.
  6. El sistema calcula el subtotal de la línea y actualiza el importe total del pedido.
  7. Simultáneamente, la app resguarda el estado actual del pedido como borrador en la base de datos local (CU-06).
  8. El preventista repite los pasos 3 al 6 para cada artículo solicitado.
  9. El preventista revisa el resumen general y pulsa "Confirmar y Enviar Pedido".
  10. La app transmite el pedido a la API REST mediante llamada HTTPS asíncrona.
  11. El servidor valida la transacción, actualiza el stock en depósito y retorna confirmación con el número de pedido registrado.
  12. La app elimina el borrador local y presenta la opción de generar el comprobante en PDF (CU-08).

Flujos Alternativos:

  • 4a. Stock en cero o insuficiente: El sistema emite un aviso visual en pantalla indicando la existencia actual, permitiendo al preventista ajustar la cantidad o sustituir el artículo.
  • 8a. Modificación o eliminación de ítems: El vendedor puede modificar cantidades o remover líneas; el sistema recalcula inmediatamente subtotales y actualiza el borrador local.
  • 10a. Interrupción de conexión de red: Si no hay cobertura de datos, la aplicación informa el fallo manteniendo el pedido seguro en la base de datos Room para su transmisión posterior sin pérdida de datos.

Postcondición: El pedido queda registrado en la base de datos central en estado pendiente de despacho y reflejado en las métricas del Dashboard.

CU-03 · Actualizar Ubicación GPS del Cliente Requisito: RF-03

Actor: Vendedor / Preventista

Precondición: El preventista se encuentra en el local del cliente con permisos de localización activos.

Flujo Principal:

  1. El preventista ingresa a la ficha del cliente y pulsa "Ubicación GPS".
  2. La aplicación abre el diálogo de mapa interactivo y obtiene las coordenadas del sensor GPS.
  3. El sistema realiza geocodificación inversa mediante el servicio Nominatim de OpenStreetMap para sugerir la dirección correspondiente.
  4. El preventista confirma la posición y pulsa "Guardar Ubicación".
  5. La aplicación envía las coordenadas a la API REST para su almacenamiento en el servidor.

Postcondición: Las coordenadas del local quedan registradas en el servidor para la optimización de las rutas de entrega.

6. Reglas del Negocio

Código Regla de Negocio
RN-01 Asociación Obligatoria de Cliente: No es posible formular ni guardar pedidos sin haber seleccionado previamente un cliente con identificador tributario (RUC o Cédula) registrado.
RN-02 Alerta y Control de Existencias: Al seleccionar productos, el sistema visualiza el stock disponible en depósito y alerta los ítems con existencia en cero para evitar comprometer mercadería no disponible.
RN-03 Definición de Condición Comercial: Cada pedido debe estipular expresamente si corresponde a la modalidad Contado o Crédito antes de su confirmación final.
RN-04 Persistencia Automática de Borrador: Todo cambio en los ítems de un pedido en confección se guarda de manera asíncrona en la base de datos local SQLite/Room para evitar la pérdida accidental de datos.
RN-05 Inmutabilidad de Transacciones Confirmadas: Una vez transmitido con éxito al servidor y aceptado por la API central, el pedido solo puede ser ajustado por personal administrativo desde el ERP de depósito.
